### Issue 1: htmlsnapshot stale after any JS interaction — no live-DOM extraction alternative for CSS workflows

**Severity:** High
**Category:** Product

#### Reproduction

1. goto form page
2. Fill form fields, check checkboxes, submit
3. htmlsnapshot get text ".result-panel" — returns stale initial HTML, not the submission result

#### Expected Behavior

There should be a way to extract content via CSS selectors from the live DOM, or htmlsnapshot should be re-capturable after interactions to reflect the current page state.

#### Actual Behavior

The docs warn that htmlsnapshot captures initial HTML only. After interactions, users must switch to 'eval' with raw JavaScript — a completely different extraction paradigm. This breaks the mental model for CSS-selector-based extraction workflows.

#### Root Cause Analysis

htmlsnapshot capture takes a static HTML snapshot at page load time. There is no 'htmlsnapshot recapture' command to refresh the stored snapshot from the current live DOM. Users must use eval (JavaScript) for post-interaction extraction, which requires different skills and selector knowledge.

#### Code Pointer

`browser4-rest/ — MCPToolController or htmlsnapshot capture handler`

#### AI Suggested Improvement

- Add 'htmlsnapshot recapture' command to re-capture the current live DOM into the snapshot store
- Or make 'htmlsnapshot get' optionally query the live DOM when passed a --live flag
- This is a critical gap for the common workflow of: interact with page → verify results

### Issue 2: get text with CSS selectors silently fails on live page

**Severity:** Medium
**Category:** UX

#### Reproduction

After form submission: ./b4w.ps1 get text ".result-panel"

#### Expected Behavior

The command should extract text from the matching element, or give a clear error that explains how to do it correctly.

#### Actual Behavior

Output: 'null' then 'No elements matched ".result-panel".' with a tip about using htmlsnapshot instead. The tip is helpful but the initial 'null' output is confusing and the naming collision between 'get' (live AX-tree) and 'htmlsnapshot get' (stored CSS) creates cognitive overhead.

#### Root Cause Analysis

The 'get' command operates on the live accessibility tree using refs (e5), not CSS selectors. CSS selectors are only supported in 'htmlsnapshot get'. The naming collision between these two 'get' commands causes confusion — users naturally try CSS selectors with 'get' first since that's the pattern they learn from 'htmlsnapshot get'.

#### Code Pointer

`cli/browser4-cli/src/commands/get.rs — the get command handler`

#### AI Suggested Improvement

- Rename 'get' to 'inspect' or 'ax-get' to distinguish it from 'htmlsnapshot get'
- Or add CSS selector support to 'get' by first trying ref matching, then falling back to CSS selector lookup against the live DOM
- At minimum, detect when the selector looks like a CSS selector (starts with . # [ or contains space/>) and immediately suggest the correct alternative before the confusing 'null' output

### Issue 3: Accessibility tree labels don't map to DOM CSS selectors

**Severity:** Medium
**Category:** Discoverability

#### Reproduction

1. snapshot -i shows 'result-panel' and 'state-log' as generic element labels
2. eval 'document.querySelector(".result-panel")' returns null
3. eval 'document.querySelector(".state-log")' returns null

#### Expected Behavior

There should be a straightforward way to bridge from snapshot-discovered elements to DOM selectors usable in eval/htmlsnapshot. The snapshot shows accessibility labels (which may be aria labels, text content, or computed names) but these don't correspond to CSS classes or IDs.

#### Actual Behavior

Had to guess ID selectors (#result-data) through trial and error. The snapshot showed 'result-panel' and 'state-log' as accessibility labels but these don't exist as CSS classes in the DOM. Users must inspect the raw HTML or guess DOM structure.

#### Root Cause Analysis

The accessibility tree labels (shown in snapshot YAML as the element name after the role) come from the computed accessible name, which may be derived from aria-label, text content, title attribute, or other sources — not from CSS class names. There is no command that shows the mapping between snapshot refs and their CSS class/ID attributes.

#### AI Suggested Improvement

- Add a 'snapshot inspect <ref>' command that shows the element's tag, classes, ID, and other CSS-addressable attributes for a given ref
- Include CSS class and ID information in snapshot output for interactive elements (e.g., 'textbox "Email" [ref=e7419] [class=email-field] [id=email]')
- The 'generate-locator' command exists but is undocumented in the main help output and requires a separate invocation per element

### Issue 7: Refs remain stable across simple form fills — docs overstate ephemerality

**Severity:** Low
**Category:** Documentation

#### Reproduction

Used ref e7417 across multiple fill operations without re-snapshotting. All fills succeeded. The docs say 'Refs are ephemeral — treat them as single-use handles' and 'Always re-snapshot after interactions.'

#### Expected Behavior

Either the docs should accurately describe when refs become stale (page navigations, DOM restructuring, reactive frameworks) vs when they remain valid (simple form fills on static pages), or the implementation should be documented more precisely.

#### Actual Behavior

Refs from the initial snapshot worked for all 4 text fills, 2 dropdown selects, and 3 checkbox operations without re-snapshotting. The blanket 'always re-snapshot' guidance adds unnecessary commands to simple workflows.

#### Root Cause Analysis

The documentation takes a conservative 'always re-snapshot' stance to prevent flaky failures on reactive pages (React, Vue, etc.), but this over-corrects for static pages where refs remain valid across many interactions. The guidance doesn't distinguish between page types.

#### Code Pointer

`skills/browser4-cli/SKILL.md — Ref Lifecycle section`

#### AI Suggested Improvement

- Add guidance distinguishing static vs reactive pages: 'On static pages, refs often survive simple form fills. On reactive pages (React, Vue, etc.), re-snapshot after every interaction.'
- Add a 'snapshot --check-ref <ref>' command to test if a ref is still valid without taking a full snapshot
- Document that auto-snapshot after each command provides fresh refs, so chaining commands without explicit re-snapshot is the intended workflow
